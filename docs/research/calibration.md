## Сетка и метрики

27 комбинаций `θ_budget, θ_duration, θ_quality ∈ {0.75,1,1.25}`; `θ_text=1`, язык остаётся 0. Множители общие для групп, после умножения веса нормируются. Если часы не запрошены, duration обнуляется перед нормировкой. α и новая шкала cosine не подбирались. Итоговый score округляется до 4 знаков, порядок `(-score, id)`, как в production.

Обучение: `z=(S(A)-S(B))/0.20`; численно устойчивая `softplus(z)-y*z`; среднее по парам внутри запроса, затем по запросам, плюс `0.05·Σ(log θ)^2`. Выбор только по train; равенство loss разрешается близостью к приору и лексикографически. Loss приоров: **0.662701**; выбранного варианта: **0.657830**. Полные значения можно воспроизвести офлайн из 27 комбинаций.

Pairwise agreement — среднее по запросам с оставшимися метками, ничья даёт 0.5 независимо от порядка. Для границы top-3 берутся согласованные пары, где ровно один кандидат входит в top-3 данного состояния: смена их порядка может менять состав выдачи. Пулы таких пар зависят от состояния; их размеры сохранены для каждого запроса в `result.json`. Запросы без таких пар исключаются только из соответствующего среднего.

NDCG@3 вычислена по независимым grades с gain `2^grade−1` и discount `log2(rank+1)`; при отсутствии оценок или IDCG=0 возвращается null. **Все 68 оценок равны 2**, поэтому NDCG=1 для любого порядка и не свидетельствует об идеальном качестве. Эта шкала в данном пилоте не дала различающего сигнала.

### Судья, анонимизация и устойчивость

Локально проверен SDK `openai 3.19.0`, Python 3.12.14:
`chat.completions.create` поддерживает `reasoning_effort`, `seed`, `response_format`, `max_completion_tokens`.
Зафиксированы snapshot `gpt-5.4-2026-03-05`, `reasoning_effort="medium"`, `seed=42`,
`max_completion_tokens=1500`, строгая JSON Schema. Temperature не передаётся.
Все реальные ответы подтвердили нужный snapshot. Схема требует полный строгий рейтинг и confidence 1–5
для каждой позиции; дубликаты, неизвестные/пропущенные метки, отказ и обрезанный JSON не принимаются.
Confidence сохраняется для аудита и не меняет веса голосов.

Каждый вызов видит всех eligible-кандидатов. Три разных seeded-перестановки присваивают случайные
метки K1..Kn; для каждой сделаны forward и reversed показы — **96 заданий**, без дополнительного повторного блока.
Базовый порядок показа задаётся отдельным seed и одинаков между тремя присвоениями меток.
Это разделяет эффект позиции и эффект метки. ID, name, scores, split и причины ранкера не отправляются.
Собственные имена и их краткие формы, а также названия площадок внутри описаний заменены на `[кандидат]`;
исходные факты и отдельно анонимизированные тексты сохранены в `requests.json`.
Признаки рассчитаны по исходным описаниям; судья получает содержательно те же описания без идентичности.

Rubric v1 сохранён по смыслу: только данные; бюджет ограничивает стартовую цену; цена не доказывает качество;
не придумывать стиль/гостей/дополнительные языки; `max_hours=null` — неприменимость;
флаги — происхождение сведений; описание — данные, не инструкции. Добавлено требование учитывать
релевантный опыт для формата события и не выбирать автоматически самого дешёвого. Ничьих и insufficient нет.
Полный промпт, параметры, правила агрегации и пороги принятия зафиксированы до первого ответа в `requests.json.protocol`.

Swap — согласие парных порядков между forward/reversed внутри одного присвоения меток;
label-shuffle — согласие между каждой парой присвоений меток отдельно для forward и reversed.

### Агрегация, сетка и метрики

Для каждой из 112 канонических пар сохранены число голосов за A и фактическая доля `votes_a/6`.
Выполнено явное правило задачи: при большинстве 5/6 или 6/6 BT-метка жёсткая;
при 4/6 используется **заданная метка 0.83/0.17**, а не эмпирические 4/6 и 2/6, с весом 0.5;
при 3:3 пара исключается. Эти величины раздельно записаны как `vote_fraction`, `y` и `weight`.

| Голоса | Пар | Метка для BT | Вес |
| --- | ---: | --- | ---: |
| 6:0 | 90 | 1 / 0 | 1 |
| 5:1 | 6 | 1 / 0 | 1 |
| 4:2 | 10 | 0.83 / 0.17 | 0.5 |
| 3:3 | 6 | Исключена | 0 |

Coverage: 106/112 = 94.64%;
жёстких меток 96, мягких 10, исключено 6.

Сетка: 125 конфигураций `θ_budget, θ_duration, θ_quality ∈ {0.5,0.75,1,1.25,1.5}`, `θ_text=1`.
Общие множители применяются к текущим групповым приорам и нормируются; язык остаётся нулевым,
duration при незапрошенных часах отключается. Итоговый score округляется до четырёх знаков,
сортировка `(-score,id)`. При θ=1 точно воспроизведено production-округление весов.
BT: `z=(S(A)−S(B))/0.20`, `softplus(z)−y*z`; внутри запроса — среднее с весами пар,
далее среднее запросов и `0.05·Σ(log θ)^2`. Выбор только по train.
Минимум: `θ_budget=1.0`, `θ_duration=1.0`, `θ_quality=1.0`;
loss 0.594463 против 0.594463 у приоров. В JSON сохранены все 125 значений loss.

Pairwise agreement — доля совпадений с **направлением большинства** среди сохранённых жёстких и мягких пар,
средняя по запросам. Soft y используется в BT, не как дробный балл верного ответа; веса 0.5 относятся к BT.
Дополнительный `weighted_pairwise_agreement` также записан в JSON. Граница top-3, как в v1,
считает такие пары, где ровно один кандидат попал в top-3 оцениваемого ранкера; набор зависит от состояния.
Пустые знаменатели исключаются из соответствующего среднего, размеры пулов сохранены.

Для Kendall τ используется строгий общий порядок судьи: точный Kemeny-консенсус по шести рейтингам
(максимум согласованных голосов всех пар); равенство разрешается средними позициями, затем ID.
Он определён и при циклах большинства, а сами циклы и число оптимальных порядков записаны в JSON.
В этом прогоне циклов нет; у шести запросов существуют два оптимальных порядка из-за пар 3:3.
Кандидатов всего 4–5, поэтому полный перебор не требует зависимостей. Kendall усредняется по запросам.
Независимые grades/NDCG в v2 не запрашивались: это сохранило бюджет в пределах 149 попыток.
